# CardFactory 对照 DSPONLINE 的单机版差距分析与续作设计

## 文档状态与权威性

- 日期：2026-08-24
- 对照源：本地 `D:\AI_Program\CardGame\DSPONLINE` 仓库当前源码与文档
- 目标工程：本仓库 `main` 分支，基线提交 `1d2030a`
- 已批准范围：在 Godot 中实现 DSPONLINE 的完整单机玩法；账号、云存档、排行榜、在线社交和服务器运维不在当前范围
- 权威口径：本文件用于定义后续功能边界和完成标准；旧的根目录对比报告只能作为历史资料，不能覆盖本文件与 `docs/PROJECT_STATUS.md`

本分析对“存在文件”“存在函数”“接入主场景”“形成可玩闭环”“有权威测试”做严格区分。只有从主场景可触发、状态真实推进、失败保持原子性且被正式测试覆盖的能力，才计为已交付。

## 目标

把 CardFactory 从目前的单行星基础生产线演示，继续建设为完整的单机 2D 无限画布工厂游戏。最终玩家应当能够：

1. 从开始菜单创建、保存、退出并恢复一局游戏。
2. 在资源、施工库存和电力约束下建设确定性的生产网络。
3. 通过手工制造、建筑升级、传送带和物流站扩大产能。
4. 完成教程、任务与科技树，逐步解锁行星和恒星系。
5. 建设戴森云、戴森球及终局巨构，达成明确的单机胜利目标。
6. 在离线后安全结算收益，并能通过统计、诊断和生产资料库解释工厂状态。

目标是复刻玩法规则、信息架构和交互意图，不复制 DSPONLINE 源码、素材、商标或在线服务实现。

## 对照方法

### CardFactory 证据

- 活跃运行树：`project.godot` → `Main.tscn` → `Main.gd`、`FactoryWorkspaceUI.gd`、`InputHandler.gd`、两个 renderer。
- 权威测试：`tools/run_tests.ps1` 当前承认 `TestBaseline`、`TestFactoryWorkspace`、`TestStatePersistence`、`TestSimulationCore` 和 `TestInventoryConstruction` 的唯一成功标记。
- 数据规模：4 个 JSON 文件共声明 38 个物品、30 类建筑和 20 条配方。
- 活跃建造范围：`ConstructionSystem` 和 `FactoryWorkspaceUI.DOCK_BUILDINGS` 支持矿机、熔炉、制造台 Mk.I、发电机 4 类，建造消耗对应施工件。
- 未挂载候选：科技、物流站、行星、星系、戴森球、存档、统计等脚本和旧 UI 文件存在，但多数没有进入主场景或模拟编排。

### DSPONLINE 证据

- `README.md` 与 `docs/PROJECT_STATUS.md` 记录 8 个恒星系、22 颗行星、78 个物品、78 条配方、37 类建筑、67 项科技、13 项成就和 32 个战役任务。
- `docs/GAMEPLAY_SYSTEMS.md` 定义生产、电力、物流、科研、戴森、离线、蓝图和设置等稳定规则。
- `src/components` 提供工厂、科技、星图、戴森、统计、蓝图、教程、离线报告等玩家入口。
- `src/game` 将内容、确定性模拟、存档、离线结算、规划、诊断和性能治理分离。

## 当前能力基线

### 已交付

- 空白工厂画布、节点卡片、输入输出端口和连接绘制。
- 四类建筑的施工件消费、矩形防重叠、拆除返还和失败原子性。
- 行星托盘、施工库存、光标载荷，以及可保存并按固定 tick 推进的基础手工队列。
- 单选、拖动、删除、端口拉线、配方选择、相机平移缩放和快捷键。
- 矿机 → 熔炉 → 铁锭的最小生产闭环。
- 连接 `enabled` 与当前帧 `active` 的状态区分。
- 顶栏、资源栏、检查器、建造坞和操作反馈。
- 版本化状态、10 个本地槽位、原子保存、备份恢复、120 秒自动保存和退出握手。
- 60 Hz 固定步长、保留式追赶预算、确定阶段顺序，以及真实作用于生产和线路的供电倍率。

### 部分交付

- 生产：支持矿机和单输入加工，但没有完整配方链、整数库存规则、副产物、增产剂或设备特例。
- 电力：全局供电倍率、燃料发电和可再生倍率已经闭环，但没有电网分区、储能、发电优先级、正式燃料补给 UI 或环境波动。
- 物流：连接能传输单一物品，但没有等级、并联、堆叠、优先级、路线、监控和物流站调度。
- 数据：声明了 38/30/20 的物品/建筑/配方，只有少量真正可建、可解锁和可模拟。
- 统计：能够生成基础摘要，但没有可靠采样窗口、历史趋势、生产定位和网络诊断入口。

### 未接入或占位

- 云存档、压缩和 Worker 等延期能力已改为明确不可用；不进入当前单机运行树，也不返回假成功。
- `TechnologySystem` 声明 10 项科技，但未进入 `SimulationEngine` 和主 UI。
- `PlanetSystem` 声明 5 颗行星，`GalaxySystem` 声明 3 个恒星系，但没有权威活动行星、独立工厂状态、殖民和跨星物流。
- `StationSystem`、`LogisticsSystem`、`DysonSphereSystem` 和相应 UI 未进入活跃运行树。
- `GalaxySystem.can_explore_system` 跳过物资检查；多个高级方法是固定成功或简化返回。
- `MiniMap.gd`、`SavePanel.gd`、`TechnologyPanel.gd`、`GalaxyMap.gd` 等旧 UI 没有挂载到当前主场景，也没有正式交互门禁。

## 单机迁移边界

### 必须实现

- 本地新游戏、存档槽、自动保存、备份、迁移和离线结算。
- 确定性生产、电力、库存、施工、手工制造、传送带和物流站。
- 完整单机内容目录、教程、任务、科技、成就和解锁节奏。
- 多行星、星图、殖民、星际物流、戴森工程和单机终局。
- 蓝图、统计、诊断、资料库、设置和必要的平台适配。
- 所有玩法命令的失败原子性、资源守恒、稳定 ID 和版本化存档。

### 可以在核心终局之后追加

- 纯本地的全星系空间站建设、每日合同和装饰。
- 内容包/Mod 注册、依赖和存档使用保护。
- 高倍率时间扭曲和超大型工厂专用结算优化。

这些能力仍属于单机，但不应阻塞第一版完整终局。

### 明确排除

- 账号注册、登录、邮箱和账号安全。
- 云存档、云修订、跨设备冲突和云配额。
- 排行榜、在线活动、玩家在线状态和遥测。
- 公共空间站主页、收藏、社交信号和服务器合同同步。
- DSPONLINE 的 Node/SQLite 服务端、Nginx/systemd、双节点发布、备份和运营后台。
- React/PWA/Electron/Capacitor 的实现本身。Godot 的 Windows/Android 导出仍可在单机产品化阶段处理。

任何云相关旧占位方法不得继续返回“成功”。在清理阶段应删除、隔离为明确的 `NOT_SUPPORTED`，或从单机接口中移除。

## 目标架构

```text
Main / AppShell
├─ StartMenu / SaveSlots / Settings
└─ GameSession
   ├─ Authoritative GameState + schema/version/migrations
   ├─ Deterministic SimulationEngine
   │  ├─ Power
   │  ├─ Production
   │  ├─ Belt + Station Logistics
   │  ├─ Research + Progression
   │  ├─ Planet + Galaxy
   │  └─ Dyson + Endgame
   ├─ Local Persistence + Autosave + Offline Settlement
   └─ Workspaces
      ├─ Factory Canvas + Inspector + Construction
      ├─ Technology / Campaign / Statistics / Codex
      ├─ Galaxy / Logistics / Dyson Planner
      └─ Blueprint / Settings / Offline Report
```

### 结构原则

1. `GameState` 是唯一权威状态；UI 不直接修改嵌套字典。
2. 所有玩家操作通过命令方法返回结构化结果，失败不改变状态。
3. 模拟使用固定步长；渲染帧率不能改变产量。
4. 存档只保存规范化领域状态，不保存可重建缓存、节点引用或临时选择。
5. 内容数据与规则实现分离；物品、配方、建筑、科技和行星引用必须在启动时完整校验。
6. 未接入主场景的旧脚本不是既成架构。每个文件都要经过保留、重写或删除判定。
7. 大规模优化必须保持同一输入得到同一状态摘要，不能用补物资或跳模拟掩盖性能问题。

## 核心领域不变量

- 库存、施工件、物流载具和科技投入不能无故生成、丢失或变为负数。
- 放置、蓝图、升级、殖民和研究开始均先验证全部条件，再一次性提交。
- 删除建筑必须确定性处理连接、缓存和返还；不能留下悬空引用。
- 连接方向、物品类型、配方输入和端口容量始终兼容。
- 电力不足按明确倍率影响设备；恢复供电后从原进度继续。
- 切换行星只切换视图和活动工厂，不混合各行星库存、建筑与连接。
- 物流中的货物始终有唯一所有者：源缓存、线路在途、载具或目标缓存。
- 存档加载、离线结算与正常模拟不能重复结算同一时间段。
- 科技、任务、戴森和终局进度必须可保存、迁移并在加载后继续。

## 实施顺序设计

### P0：可信地基

- 版本化 GameState、序列化 codec、迁移、完整性校验。
- 开始菜单、槽位、自动保存和安全退出。
- 固定步长模拟、电力真实作用、零错误/零假成功边界。
- 清点并隔离高级占位代码。

### P1：完整行星工厂

- 行星物资托盘、施工库存、手工制造和资源返还。
- 扩充生产设备与配方，完成电力/生产/缓存闭环。
- 传送带等级、配置、批量编辑、多选和蓝图。

### P2：推进与可解释性

- 正式教程、战役任务、科技树、成就与解锁。
- 统计、阻塞诊断、生产资料库和链路定位。
- 内容目录补齐到批准的单机基线。

### P3：多行星工业

- 每行星独立工厂、矿产和殖民状态。
- 星图、恒星系探索、行星物流站、星际物流站和载具调度。
- 跨行星资源链与黄色/紫色/绿色矩阵推进。

### P4：戴森与终局

- 太阳帆轨道、戴森云、火箭、壳面和射线接收。
- 白矩阵、终局巨构、胜利状态、离线报告和安全时间扭曲。
- 可选的纯本地空间站扩展在完整终局之后进入。

### P5：产品化与扩容

- 设置、国际化、主题、键盘/手柄/触摸和无障碍。
- 小地图、LOD、空间索引、性能预算和大型存档夹具。
- Windows/Android 单机导出、崩溃恢复说明和发布检查单。

## 验收策略

每个阶段必须同时满足：

1. 从正式入口可触发，不依赖测试场景或调试调用。
2. 新增规则有先失败后通过的领域测试。
3. 关键玩家路径有场景级输入/输出回归。
4. 保存—退出—加载后，相关状态与进度保持一致。
5. 失败路径不扣资源、不创建半成品、不污染选择或临时状态。
6. `tools/run_tests.ps1`、主场景无窗口启动和 `git diff --check` 全部通过。
7. `docs/PROJECT_STATUS.md` 只在上述证据完成后更新状态。

“代码行数”“存在类或函数”“旧测试打印 PASS”“面板能实例化”均不能单独作为完成证据。

|---|---|
| 旧代码制造虚假完成感 | 按运行可达性和权威测试重新分类；占位 API 不计完成 |
| 在松散字典上继续叠功能 | 先冻结 schema、codec、迁移和验证器，再扩系统 |
| 一次迁移全部内容导致失控 | 每阶段交付一个可玩的纵向闭环，并设置停止门 |
| UI 先行但规则不守恒 | 先领域命令和失败测试，再接 UI |
| 模拟结果依赖帧率 | 固定步长、状态摘要与差分测试 |
| 大型工厂过早优化 | 先建立确定性基准，再引入索引、LOD 和批处理 |
| 许可与原创性风险 | 只参考行为与信息架构；不复制源码、素材、商标和在线资产；商业用途需另行确认授权 |

## 成功定义

当玩家可以在不联网的情况下，从新游戏开始，通过可保存、可恢复且规则确定的生产、电力、物流、科技、星际工业和戴森建设流程，达成明确的单机终局；同时所有主要失败路径都有可见原因和自动回归证据，才可以称为“完整单机玩法对齐”。

在此之前，项目状态应使用“阶段 X 已交付”而不是笼统的“DSPONLINE 已复刻完成”。
