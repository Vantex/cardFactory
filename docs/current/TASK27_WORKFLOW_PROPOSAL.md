# 任务 27 工作流调整方案

2026-10-07。用户已要求采用本方案继续完成任务 27，现为执行工作流。范围和发布条件沿用 [原任务计划](TASK27_PLAN.md)。当前批次、阻断和新验证记录见 [执行进度](TASK27_PROGRESS.md)，逐项归组见 [对齐清单](../testing/dsponline-parity-checklist.md)。

建议采用：**一次归组盘点 → 按完整玩法链合批 → 批内集中定位和修复 → 分层验证 → 里程碑验收 → 最终发布门。**

## 为什么需要调整

当前方法把较小的规则修复分别做成了完整交付批次，反复处理候选副本、源夹具、主树验证、三种渲染方式的包检查、收据复审和多份文档。原计划已允许复用未变证据、只运行相关检查；实际执行仍付出了大量重复成本。

采矿、资源模式、初始储量几批解决了真实问题，但矩阵一直保持 262 个已验证 key，完整成长旅程仍未闭合。这说明投入主要用于前置修复和证明维护，不能用日志、保存文件或断言数量衡量交付进展。

本次只读汇总当前 manifest：

| 尚待验收的类别 | 数量 | 处理方式 |
|---|---:|---|
| 命令与回调 | 624 | 按领域和玩家操作归组，区分领域命令、查询和 UI 转发；每个 key 保留具体断言 |
| 内容定义 | 175 | 随所属玩法验证实际效果，适用时使用参数化案例 |
| 工作区 | 12 | 随玩法链检查正式入口、交互、反馈和状态接续 |
| 合计 | 811 | 不代表 811 个独立功能，也不代表实际开发量 |

剩余条目中 514 项为“实现中”、297 项为“未实现”；另有 262 项已验证、26 项在线排除。登记状态不是对真实缺失数量的新判断。

## 1. 一次盘点，形成有限的交付批次

复用现有 [对齐清单](../testing/dsponline-parity-checklist.md)、manifest 和测试入口，不新建另一套平行台账。

- 第一遍覆盖全部 811 项：按玩法链归组，关联现有实现、正式入口和已有断言。证据不足标“需核实”，不对每个函数展开深度审计。
- 进入一个批次前，再把该批条目判为“已有证据缺登记”“已有能力缺源比较”“真实行为差异”“真实能力缺失”，据此决定补登记、补测试还是改产品。
- 每批写明：玩家能完成什么、涉及哪些 key、依赖哪个前批、具体阻断和退出条件。按共享状态和业务契约合批，不为凑数量合并无关改动。
- 已通过的源夹具和行为证据按依赖复用。禁止从原生结果反推源期望，不重跑矩阵生成器覆盖人工映射。

第一遍归组后即可开始首批；未知细节在所属批次解决，避免盘点变成无边界全仓审计。

## 2. 以玩家旅程组织实施

建议顺序如下；精确 key 集合在盘点后填入现有清单，不预先承诺登记数量。

| 批次 | 可交付的玩法闭环 | 本批重点 |
|---|---|---|
| B1 资源与开局 | 新游戏 → 手采/自动采矿 → 输出缓存 → 领取/运输 → 制造、首项研究 → 保存重开 | 收拢当前手采候选、容量、旧小数和资源所有权；复用已验证研究与配方 |
| B2 工厂成长 | 扩建供电与生产 → 施工/蓝图/统计 → 六色矩阵及科技成长 | 补玩家操作和成长依赖；已有证明只在受影响时刷新 |
| B3 多行星物流 | 真实殖民 → 行星生产 → 跨星运输及高级物流 → 保存接续 | 托盘、载具、在途货物、翘曲器和共享预算守恒 |
| B4 终局系统 | 戴森及终局 → 空间站/合同 → 银河出口与枢纽 | 解锁、投入、结算和跨系统效果 |
| B5 模式与恢复 | 适用旅程的普通/速通、三档难度、时间扭曲、纯挂机、内容包及异常恢复 | 在前批普通保存检查基础上补特殊模式和事务中断边界 |
| B6 发布收口 | 全部逐项证明、自动成长、人工旅程、独立 Windows 包和最终检查 | 按原 27C～27E 条件交付 |

**完整成长链从 B1 开始持续延长，不能等所有专项结束才运行。** 每阶段保存由实际游玩命令产生的检查点，记录前序输入、规则和版本。局部迭代可从有效检查点继续；上游规则变化则从受影响位置重建。最终仍从干净开局运行适用完整旅程。

可以自动推进正常模拟步，但不能注入材料、科技或殖民结果冒充赚取成长。受控数值矩阵单独保留，用来覆盖完整旅程难以自然出现的边界。

## 3. 批内集中诊断，缩短修复反馈

1. 明确该链的源行为、状态所有者、数值语义和兼容边界，统筹正常路径、容量边界、失败无副作用和保存接续。
2. 对可信且可独立运行的案例汇总差异，按共同根因归组。解析失败、环境失效或测试前置不成立时先修运行基础，不把后续无效输出当作业务差异。
3. 对已定位的同类问题集中修复；编辑期间运行便宜的相关断言，及时捕获错误，不等批末才首次运行。
4. 批次稳定后做一次领域集成验证和有界独立审查。复审只检查修复及影响，未变材料通过引用复用。
5. 满足退出条件后接入、登记具体 key，并推进下一条链。没有新增 key 的前置工作须注明解除了哪个具体阻断，不能无限拆出新“前置批次”。

资源复制、数据损坏或共同基础层问题阻止相关批次接入；其他范围外发现登记到对应批次，不因此扩大当前闭环。

最多同时维护一个集成候选。确有独立工作时可委派源契约核对、缺口归组或只读审查，写明输入、边界和交付条件；共享状态的连续修改由主 Agent 统一完成。不要让多个 Agent 并行写同一领域系统，或同时运行会污染性能结果/用户目录的进程。

## 4. 按变化范围安排验证

| 时点 | 必须验证 | 避免重复的部分 |
|---|---|---|
| 根因修复 | 修改前失败证据、修改后相关断言；脚本/导入检查及必要边界 | 无关领域全量检查、完整打包 |
| 玩法批次稳定 | 源对照矩阵、所有受影响领域、正式 UI 入口、保存/恢复与兼容类别、独立审查 | 输入、依赖和环境未变的其他领域证据 |
| 跨系统里程碑 | 当前成长链、扩大后的集成回归；涉及包资源/运行差异时做导出包验证 | 每个小修复后的全渲染器纯数值矩阵 |
| 最终候选 | 原任务全量门、完整逐项对齐、当前包、1080p 产品门、人工记录、性能与最终审查 | 历史局部通过不能替代最终验收 |

压缩重复成本的具体方式：

- 纯数值和源对照矩阵主要在 headless 层执行；渲染器差异检查实际渲染、输入、资源加载及必要包内集成。包与编辑器语义一致性仍需证明。
- 参数化案例覆盖全部相关规则；磁盘往返按不同持久状态和风险类别选择，例如未满/满仓、部分领取、旧小数、多所有者、中断事务。避免把全部组合重复保存，也不能漏掉因数据不同而改变的序列化行为。
- 源导出、行为比较、磁盘保存、图形验证分开计时。先消除已知重复，再根据实测耗时优化，不承诺未经测量的提速倍数或完成日期。
- 复用条件包括相关产品依赖、测试及夹具输入、引擎和影响结果的环境；依赖不清楚则扩大检查。不能只因某一个脚本没改就复用依赖它的旧证明。

**现有硬门槛保留。** 若调整 runner 结构，先证明必需断言仍被执行、失败仍拒绝登记，再采用新分组。最终必须运行 `tools/run_tests.ps1`（当前声明 58 场景，后续新增正式测试也须纳入）、冻结源哈希/归属检查、`check_dsponline_parity.ps1 -RequireComplete` 及原计划其余发布检查。

工具改造只按需要补现有 runner 的测试选择、计时和统一结果输出，默认完整运行语义不变。不另建测试平台、调度服务或层层审计系统。

## 5. 减少交接成本，按实际交付报告进展

现有清单承载逐项映射；`TASK27_PROGRESS.md` 顶部保留当前批次、下一步和阻断项。运行报告保存退出码、成功标记、错误检查、输入/版本、耗时和证据路径。保留旧日志，不在每批重新审计未变历史。

每批汇报只回答：哪条玩家操作链闭合、哪些具体 key 新获有效证据；哪些真实缺口已修复、哪些仍阻断；本轮新跑/复用了什么、还有哪些未验证边界。

不再向交接、状态、索引、路线图、计划和发布清单复制同一段长记录。批内更新执行记录；里程碑及最终交付再同步其他文档，并引用同一证据。

任务结束仍需全部 1073 个非在线 key 通过、适用完整旅程有证据、发布包与原性能门满足、最终审查完成并交付本地 main。人工旅程当前缺少原生 Windows 控制能力，提前准备最小操作清单并保持待验收；自动按钮调用不能替代人工结果。大型工厂 60 FPS 不能从现有局部通过推断。

## 6. 从当前现场切换

恢复实现时按以下顺序，不丢弃已有有效工作：

1. 只读固定当前 MAIN、隔离手采候选、通过/失败记录和未解问题；不以重新接手为由重跑旧完整基线。
2. 完成剩余条目的第一遍归组，确定 B1 的 key、源契约、最小回归集合和退出条件。
3. 在同一个资源流转批次内复现并处理当前审查提出的两项风险：多所有者小数扣减失败后传送带仍可能入账；手采按取整库存计算空位可能超过容量。两项均需原生 Godot 失败证据，不能把审查意见写成修复通过。
4. 统一验收手采、自动采矿、领取、相关运输、旧档和正式入口，接续干净开局的实际制造/首研究路径；只登记实际覆盖的 key。
5. B1 满足退出条件后推进 B2；完整打包和广泛复审留到上述触发点。

原方案制定时的恢复位置（历史；当前状态见[开发现状与续作指南](DEVELOPMENT_HANDOFF.md)）：

- MAIN 最近已闭合到初始储量批；矩阵仍为 262 已验证，没有接入手采产品修改。
- 手采候选：`.godot/task27-manual-probe/`；源输出和局部日志：`.godot/task27-next-resource-manual/`。已有局部通过不能表示候选整体通过。
- `candidate-focused-exits.json` 保留当时 7/8 通过及原边界探针失败；后续边界修正通过另见 `candidate-boundary-final.log`，不改写原失败记录。
- `candidate-freeze.json` 写入后边界测试脚本发生修改，不能将它视为当前所有测试输入的完整绑定。
- 两项新浮点风险尚未完成 Godot 复现/修复；完整当前场景门、完整成长、手采候选包和人工验收均未完成。
- 保留用户 `project.godot` 修改，冻结参考源只读，不操作 `recovery-baseline`，本轮不提交或推送。
